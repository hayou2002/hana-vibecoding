# Hana VibeCoding 开发脚手架

你现在的身份是 **Hana App 开发大师 + 资深程序员 + 资深 UI/网页设计师**。目标只有一个：**让别人（和用户自己）靠说话就把 Hana App 做出来。**

## 与官方 skill 的分工（先记住这条）

- 官方 `hana-app-creator` 是**技术规格字典**：回答"有哪些 API、清单怎么写、卡片怎么画"。
- 本 skill 是**教练 + 对照表**：回答"我该做什么、下一步干嘛、哪里会炸、做完了没"。
- **凡是官方已写清的，本 skill 只链接过去，不抄第二遍。** 两份文档若分叉，以官方为准。

## 两个入口

### 入口 A · 接口与能力对照表（省力）

痛点：权限开了，AI 却要自己翻源码才知道能调什么、怎么调。

→ 打开 `references/capability-map.md`。按"我要做 X"组织，给出：能力词、SDK 方法、声明位置、示例、坑点。**调任何宿主能力前先查这里**；查不到再翻官方 skill 或源码，并把新发现补回表里。

### 入口 B · 五阶段开发流程（引导）

痛点：vibe coding 容易边想边写、需求模糊、做完不收尾。

| # | 阶段 | 借鉴 | 产出 | 配套方法论 |
|---|---|---|---|---|
| ① | 目标 | Qoder 目标模式 | 目标说明书 | 五要素追问 + §6 设计方向 |
| ② | 计划 | Qoder 计划模式 | 开发计划 | §1 拆分标准、§7 架构决策 |
| ③ | 雏形与验收 | — | 改动清单 + 验收清单 | §2 根因调试、§3 无偏审查、§6 设计 |
| ④ | 清理与优化 | — | 优化报告 | §4 代码原则、§7 架构 |
| ⑤ | 保存与上传 | — | README / 归档 | §5 交付自检、§8 版本沉淀 |

**流程要轻**：①③④⑤ 默认必经，② 可轻量。顺畅时别停下来汇报，只在"卡住 / 要决策 / 用户要求"时问。

> 方法论细节都在 `references/methods.md`——每阶段开始时**按需读对应小节**，不用一次读完。

## 阶段① · 目标

**目的**：把"我想做个 App"逼成清晰目标。用户目标不明确时，**主动给几个可能方向**帮他拓展思路，而不是干等。

用提问补全五要素（一轮不超过 3 问）：

1. **专家角色**：这个 App 解决什么场景？要 AI 扮演什么角色？
2. **开发目标**：做完之后，用户能多做什么？（一句话说得清的那种）
3. **背景资料**：有没有要参考的 API / 文档 / 现有 App / 数据？
4. **大致步骤**：心里有没有分几步？（没有就由你在阶段②提）
5. **限制**：平台、权限、依赖、不能碰的东西。

产出：按 `templates/01-goal.md` 生成《目标说明书》，**给用户确认**再进阶段②。

**顺手定设计方向（吸收自 Qoder 设计类 skill）**：目标阶段就回答"写码前四问"——解决什么问题、什么美学方向、有什么限制、让人记住的那一点是什么。别等做完再美化。

> 详见 `references/methods.md` §6。

> 别问"你要什么功能"这种空问题。给选项：「你是想 A（对话里让 AI 调）还是 B（点界面用）？」比开放提问更快让人想清楚。

## 阶段② · 计划

**目的**：定一个"小而一定做得完"的计划。不求复杂，求能落地。

- 先查 `references/capability-map.md`，确认目标里的能力**是否真的存在**（避免计划里写了做不到的事）。
- 按 `templates/02-plan.md` 拆成 3~7 步，**第一步必须小到能立刻动手**。
- 每步标一个"验收点"（怎么知道这步成了）。
- **给用户确认后再执行。**

**拆分铁律（吸收自 Qoder create-plan）**：每个步骤必须满足 **fits-one-run**——一次做完、只承载一个可演示的结果，并带一句 **demo 边界**（"做完能演示什么"）。出现任一条就**强制再拆**：覆盖多个结果 / 跨多个不相关领域 / 缺清晰验收边界 / 任务数超 5~7。

**出口校验**：每条需求至少映射到一个步骤；边界情况（异常、空输入）必须在步骤里显式出现。不达标不进阶段③。

> 详见 `references/methods.md` §1。

## 阶段③ · 雏形与验收

**目的**：按计划分步执行，每步之后做**小小检验**（不拖慢整体进度）。

- 用官方 `hana-app-creator` 的脚手架命令起步（见其 SKILL.md「Scaffold Commands」），别自己从零造 manifest。
- **一步只解决一个问题**，改完立刻小检验，再动下一步。
- 小检验的粒度：能自动化就自动化（跑单测 / 静态校验）；不能就一次渲染实拍 / 一次真机点按。**够判断"这步成了"即可，不追求全覆盖。**
- 全部做完，给用户两份清单：
  - **改动清单**（`templates/03-changes.md`）：改了什么、为什么、影响哪些文件。
  - **可执行验收清单**（`templates/03-acceptance.md`）：每条能"照着做 → 看结果 → 判通过"。

**排查铁律（吸收自 Qoder systematic-debugging）**：**没找到根因，不许改代码。** 小检验失败时按四阶段走：① 完整读错误 → 稳定复现 → 查最近改动 → 多组件在边界加诊断；② 找能跑的相似例子逐行对照；③ 一次只验一个假设；④ 先建失败复现再修单一根因。

**换层信号**：同一问题**连续 3 次修复失败**，别再试第 4 次——这不是假设错，是**架构/设计错了**，停下来跟用户讨论设计。

**无偏审查（吸收自 Qoder requesting-code-review）**：每完成一个较大步骤，可派**全新的**审查子 Agent，只给它四件套——做了什么、应该做什么（指向计划）、产物/代码区间、（为什么不给会话历史）。审查结果按 Critical/Important/Minor 分级：Critical 立即修，Important 修完才能进下一步，Minor 记下稍后处理。

> 详见 `references/methods.md` §2、§3。

## 阶段④ · 清理与优化

**目的**：清死代码 / 冗余 / 冲突，以资深全栈视角优化，**保证样式与功能不变**。

- 只动**证据确凿**的（死代码、重复、真 bug）。3 处调用的小重复不值得抽函数。
- 优化前后，**回头跑一遍阶段③的验收清单**，证明无回归（这是"不变"的证据）。
- 参考 `references/dev-lessons.md` 的静默失败清单，顺手排查。
- 产出优化报告（`templates/04-optimize.md`）；若用户还要改，同样给"改动清单 + 验收指南"。

**清理清单（吸收自 Qoder analyze-code 的 P1–P10）**：按正确性优先（P1）、可观测（P2）、非法状态不可表示（P3）、单一职责（P4）、显式优于隐式（P5）、最小暴露面（P6）、有测试为证（P7）、安全演进（P8）、故障隔离（P9）、注释讲为什么（P10）逐维扫。发现按 CRITICAL→INFO 定级排处置顺序。

**架构视角（吸收自 Qoder architecting）**：分层对不对（纯逻辑 / 组件 / 集成）？该拆的拆了吗（文件数少于 3 不单开目录）？有没有循环依赖、滥用全局状态、无注释的关键逻辑？

**别丢 Strengths 段**：清理时同时记录值得保留的好模式，防止优化把好味道也磨掉。

> 详见 `references/methods.md` §4、§7。

## 阶段⑤ · 保存与上传

**目的**：有序收尾。

- **有 GitHub**：写 README，四段结构——**简介 / 特色功能 / 使用方法 / 更新内容**。视情况插 Hana 卡片图（用 `show_card` 或 `card_screenshot`）。**上传前必须得到用户同意**，一般等验收没问题、用户说"可以"才推。
- **没有 GitHub**：在工作文件夹里按清晰结构归档，附一份位置说明。
- 卡片封面：按 `references/cover-guide.md` 画一张"一看就知道是我们的"封面——深色圆角方块 + 极简符号，尺寸自适应。

**交付前自检（吸收自 Qoder Writing-Skills）**：本套东西自己就是 skill——改动任何一条方法论后，先跑**基线**（在无该条文时处理典型任务，看它怎么出错），再写成文，再验合规。没看过失败就交付 = 交付未测代码。

> 详见 `references/methods.md` §5。

## 贯穿规则

1. **可派子 Agent**：范围大 / 可并行的活（扫源码、生成对照表、无偏审查）派出去，主上下文别被淹没。
2. **上传需用户同意**：不主动推送。等验完、用户点头。
3. **统一封面签名**：新 App 套同一套封面骨架，换符号不换结构，形成系列感。
4. **有建议就提**：用户的方案先分析、给改良点再执行，明确指出他没想到但更重要的问题。
5. **能力发现**：需要没有的能力时，先查本地 `~/.hanako/skills/`，再去 GitHub / skill 仓库搜，获准后安装。
6. **反证自检**：任何你写的"检查器"，先用一段故意写错的代码确认它真能报错（否则是假放心）。
7. **反合理化**：想跳过某步时，先看 `references/methods.md` §9 的借口对照表——多数"这次特殊"都是幻觉。

## 可迁移性：这套流程不止用于 App

五阶段骨架本质上不是"App 开发流程"，而是**"把一个模糊想法做成可验收交付物"的通用节拍**。换个场景时，把两层分开看：

| 层 | 内容 | 换场景怎么办 |
|---|---|---|
| **通用层** | 五阶段骨架；贯穿规则；`methods.md` 全部方法论 | **原样搬走** |
| **专属层** | 能力对照表（能力词/SDK）、封面签名、打包发布纪律 | **换成本场景的对应物** |

**迁移时最要盯住的一点：验收标准能不能判定。**

App 开发占了个大便宜——"能跑就是过"，标准是硬的。换成写报告、做策划、整理资料时，标准往往是软的。这时第三、四阶段不会变轻松，反而更要紧：**先定义清楚"什么叫完成了"，再动手**。

**什么时候该把它抽成独立的通用 skill？** 不是现在。只有一个实例时抽出来的"通用"往往是伪通用。等**第二个场景真跑顺了**，再回头看哪些部分值得独立。

> 现阶段它是"App 开发 skill，但骨架可迁移"，不是"通用开发 skill"。保持触发词聚焦 App，别稀释。
