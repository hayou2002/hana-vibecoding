# 五阶段流程详文（按需读，别整份读）

> SKILL.md 只放决策表和通过清单；这里的每节是"怎么做"的引导、示例与代码块。
> 用法：进入某阶段时 `grep -n "^## 阶段" references/flow.md` 拿行号，只读对应一节。

## 阶段① · 目标〔第 1 步·想清楚〕

用户目标不明确时，**主动给几个可能方向**帮他拓展思路，而不是干等。

用提问补全五要素（一轮不超过 3 问）：

1. **专家角色**：这个 App 解决什么场景？要 AI 扮演什么角色？
2. **开发目标**：做完之后，用户能多做什么？（一句话说得清的那种）
3. **背景资料**：有没有要参考的 API / 文档 / 现有 App / 数据？
4. **大致步骤**：心里有没有分几步？（没有就由你在阶段②提）
5. **限制**：平台、权限、依赖、不能碰的东西。

产出随风险而定：T0/T1 直接从明确目标进入实现；只有关键取舍会改变行为、安全、数据、成本时才询问。T2 使用 `templates/01-brief.md` 对齐目标、成功标准、非目标和短计划，一次说明，不拆成多轮确认仪式。

**有 UI 改动时再定设计方向**：解决什么问题、什么调性、有什么限制、让人记住的那一点是什么；非 UI 任务不套视觉问题。

> 别问"你要什么功能"这种空问题。给选项：「你是想 A（对话里让 AI 调）还是 B（点界面用）？」比开放提问更快让人想清楚。

详见 `references/methods.md` §6；对话姿势见 §10。

## 阶段② · 计划〔第 1 步·想清楚〕

定一个"小而一定做得完"的计划。不求复杂，求能落地。

- 对 capability、manifest、权限有依赖时，查 `references/capability-map.md` 和相应官方文档，确认能力存在且授权范围合适。
- T2 使用 `templates/01-brief.md` 的第二部分，将工作拆成有依赖顺序的垂直切片；粒度由可演示结果和验证边界决定，不要求凑足固定步数。
- 每步标明可观察产出和最接近风险的验证方式；简单 T0/T1 在对话中简要列验收点即可。
- 只有计划包含重要未决取舍时才暂停等待确认；用户已明确范围的本地实现不重复要求确认。

**拆分原则**：T2 的每个步骤以可独立验证的垂直结果为单位，并说明 demo 边界。若跨不相关领域、同时承载多个结果或没有验收边界，再拆分；不为达到固定步数而拆。

详见 `references/methods.md` §1。

## 阶段③ · 雏形与验收〔第 2 步·做与验收〕

按适合的粒度实现并做**与风险相称的检查**（不拖慢整体进度）。

- 开工先看适用的 `AGENTS.md`、README/项目说明、相关代码与 `git status`，保留已有改动。项目有 `dev-state.md` 时读取并沿用；只有工作确实跨会话、多轮或需要交接时才新建/更新，结束后同步真实进度与遗留。
- 用官方 `hana-app-creator` 的脚手架命令起步（见其 SKILL.md「Scaffold Commands」），别自己从零造 manifest。
- **一步只解决一个问题**，改完立刻小检验，再动下一步。
- 小检验的粒度：能自动化就自动化；不能就一次渲染实拍 / 一次真机点按。**够判断"这步成了"即可，不追求全覆盖。**
- **静态门禁先行**：改完 Hana App 源码跑 `node scripts/check_app.mjs <app目录>`。ERROR 必须修复并重跑；WARN 需人工核对并说明处置。此门禁只检查静态模式，不替代宿主运行时测试。

**Git 检查点按需建立**：用户明确要求 commit 后，按有意义的验收/恢复边界提交；实现请求本身不自动授权提交。提交前区分已有修改与本次改动，只暂存相关文件，先检查暂存区。以下路径仅为示例，须替换成仓库中实际的本次改动路径：

```
git status --short                                      → 核对已有与本次改动
git add skill/hana-vibecoding/src/panel.js skill/hana-vibecoding/ui/panel.css
git diff --cached --stat                                → 只包含本次相关路径
git diff --cached                                       → 检查暂存内容后再提交
```

**排查缺陷**：先读错误并定位最可能的故障边界；按影响和复杂度深入调查。对复杂、反复或跨层故障，按四阶段走：① 完整读错误 → 稳定复现 → 查最近改动 → 沿组件边界加诊断；② 对照可运行的相似实现；③ 一次只验一个假设；④ 建立可复现检查后再修单一根因。小而明确的修复不必完成整套仪式。查资料顺序与“卡两次就换角度”的强制触发见 `references/methods.md` §11。

**换层信号**：同一根因经数次有证据的修复仍未解决时，停止堆补丁；重新审视假设、边界和设计，必要时再与用户对齐。次数是提醒，不是把所有故障武断定性为架构问题的证明。

**独立审查按风险使用**：跨层、安全/数据迁移、高影响或用户要求审查时，适合独立复核再交付。审查者应拿到目标/验收、准确改动范围和必要证据；按 Critical/Important/Minor 处置。小修不强制派 Agent；没有独立审查资源时如实说明，不把自查说成独立审查。

**交付**：T2 或复杂发布使用 `templates/03-delivery.md`，小任务在回复中报告改动和验证。逐项区分静态检查、Hana 宿主实测、发布端回读和未验证部分；不能用“脚本通过”概括尚未做的运行时验收。

详见 `references/methods.md` §2、§3。

## 阶段④ · 清理与优化〔第 3 步·收尾〕（T2 可选）

先判要不要做：只有真发现死代码 / 重复 / 真 bug 才进这一阶段；没发现就**直接跳过，也不写优化报告**。

清死代码 / 冗余 / 冲突，以资深全栈视角优化；目标是保持既有行为和样式，结论由相关回归检查支持。

- 只动**证据确凿**的（死代码、重复、真 bug）；小范围重复不自动构成重构理由。
- 参考 `references/dev-lessons.md` 的静默失败清单，顺手排查；跑一遍 `check_app.mjs` 收尾。
- T2 或用户要求可追溯报告时才用 `templates/04-optimize.md`；小范围修正纳入普通交付说明。

**"不变"要拿证据说话**——记录优化前后修订/差异并重跑相关验收。只有用户明确要求提交时才建立 Git 检查点：

```
git diff --stat BASE..HEAD                              → 优化变更范围
<运行相关验收>                                           → 记录真实结果与未覆盖项
```

**优化前后回头跑一遍阶段③的验收清单**——这是"无回归"的另一半证据。

**清理清单**：按正确性优先（P1）、可观测（P2）、非法状态不可表示（P3）、单一职责（P4）、显式优于隐式（P5）、最小暴露面（P6）、有测试为证（P7）、安全演进（P8）、故障隔离（P9）、注释讲为什么（P10）逐维扫。发现按 CRITICAL→INFO 定级排处置顺序。

**架构视角**：分层对不对（纯逻辑 / 组件 / 集成）？该拆的拆了吗（文件数少于 3 不单开目录）？有没有循环依赖、滥用全局状态、无注释的关键逻辑？

**别丢 Strengths 段**：清理时同时记录值得保留的好模式，防止优化把好味道也磨掉。

详见 `references/methods.md` §4、§7。

## 阶段⑤ · 保存与上传〔第 3 步·收尾〕

- 只有用户需要可分享/安装的项目交付或明确要求时才更新 README；按需采用**简介 / 特色功能 / 使用方法 / 更新内容**结构。视情况插 Hana 卡片图（用 `show_card` 或 `card_screenshot`）。
- **没有 GitHub**：在工作文件夹里按清晰结构归档，附一份位置说明。
- App 需发布安装包时，卡片封面按 `references/cover-guide.md` 制作；本地实现无需为流程额外造封面。

**对外动作逐项授权**：commit、push、创建 tag、公开 Release、提交市场 PR 各自独立。执行前确认用户明确授权了具体动作与目标仓库、分支/修订、版本、附件或 PR 内容。一次确认可覆盖一份完整列明的发布计划；任一目标或产物改变，重新确认。不得因“帮我做完”“赶时间”或希望最终上架推断当前发布授权。

**已有验收产物的发布**：需求与实现已验收时，不重做开发阶段或整套验收。确认产物来源、复用已有验收证据，只补打包/发布新增的风险检查，按“组装 → 一处完整性检查 → 发布 → 目标回读”各执行一次。先核对目标仓库、Release、市场登记与更新方向，避免覆盖或重复创建；发布命令失败先读完整报错并修正根因，同类失败最多主动修正一次，仍失败就报告已成功部分、卡点和下一步。发布或市场条目已在目标侧回读成功时停止，不再重复发布。

**用户已授权发布后，顺序不能反**（顺序错了 tag 会打在旧提交上）：

```
git push                                  → 先把代码推上去
git tag -a v0.3.0 -m "清理优化版"          → 打在刚推的 HEAD 上
git push --tags                           → 再推标签
gh release create v0.3.0 ... <zip>        → 最后建 release，附 zip 资产
```

**打包成 zip 一起发**：别人下载 zip 就能直接安装，不用自己 clone 再打包。zip 里装 `skill/<name>/` 整个目录。

**历史纪律**：

| | 放哪 | 留多少 |
|---|---|---|
| 开发碎步提交 | 本地或 `dev` 分支 | 遵循项目现行协作约定 |
| 版本提交 | `main` | 遵循项目现行发布约定 |
| 标签 | tag | 每个 release 一张 |

不要为了保持固定提交数擅自 squash、改写历史或重建 main。已公开历史不可改写；任何历史整理都必须有项目明确规范和用户对目标的授权。

**交付前自检**：本套东西自己就是 skill。改行为规则时，先更新 `eval/tasks.md` 中的固定场景和可观察判据，再修改规则；对照相同场景检查规则前后会改变什么决定。无法运行独立基线或 Agent 对拍时明确记为未测，不编造 RED/GREEN 结果。

详见 `references/methods.md` §5、§8。

### ⑤b 上架官方拓展市场（用户点名才进）

市场投稿是独立的可选发布目标。仅当用户明确要求投稿时读取 `references/market-enrollment.md`；先准备并核验 packer 产物、目标 Release 和 PR 内容，分别按上文授权规则处理公开 Release 与市场 PR。不得因用户想“以后能搜到”就提前公开或投稿。投稿前重新核对市场仓库当前 `CONTRIBUTING.md`、schema、workflow 与目标分支状态；本手册是执行摘要，不保证替代实时规则。已在市场登记的项目优先更新现有 approvals，不重复新建 registry 条目；市场索引回读命中当前 Release 后才算同步完成。

## Git 使用规范（贯穿 ③④⑤）

**别把 git 只当"存档"**：`git diff` 摊开改动范围，获准的提交提供可回退检查点；两者都不能代替行为验收。

| 阶段 | 什么时候动手 | 用它干出什么 |
|---|---|---|
| ③ 雏形与验收 | 用户已要求提交时，在有意义的验收点 | 只暂存本次路径，复核 staged diff 后提交 |
| ④ 清理与优化 | 仅在确实做优化且获准提交时 | 记录优化前后范围，重跑相关验收 |
| ⑤ 保存与上传 | 仅在具体发布动作获授权后 | `push → tag → push --tags → release` |

**别为走流程而提交**：T0/T1/T2 都不隐含 commit 授权。用户要求提交时，提交应是有意义的检查点。

**如实报告 Git 动作**：简要说明已执行命令及结果；没有执行提交或发布时，不写成已完成：

```
git commit -m "feat(panel): 五标签重构"      → a1b2c3d
git diff v0.2.0..v0.3.0 --stat              → 6 files, +412 -198
git tag -a v0.3.0 -m "清理优化版"            → 打在 e4f5a6b
```

报告命令、结果和它能证明的范围；不要求为了回复格式执行额外 Git 命令。

**提交规范**：用户要求提交时遵循仓库现有约定；没有约定时可用 `<type>[scope]: 描述`。
**一次提交一个主题**：只在获准提交时应用，不把无关改动混在一起。
**提交边界**：用户明确要求 commit 后，可按该范围提交，无需重复索取同一授权；仍须检查 Git 状态、只 stage 本次路径并复核 staged diff。commit 不授权 push、tag、Release 或市场投稿。
**双轨语言**：对用户只用大白话（"存档"/"回到之前某个存档"），术语首次出现时解释。
