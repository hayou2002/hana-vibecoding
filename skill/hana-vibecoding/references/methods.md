## §1 计划拆分标准（阶段②）

**目标**：把需求拆成"小而一定做得完"的步骤。

**T2 计划原则**：每个步骤尽量 fits-one-run——一次能做完、只承载一个可演示的结果。简单 T0/T1 不为套用拆分模板而造步骤。

**再拆信号**（按任务判断）：
1. 覆盖多个可演示结果
2. 跨多个不相关领域 / 模块
3. 缺清晰的验收边界
4. 含多个大阶段
5. 需要拆分以便独立验证或恢复

**每条步骤必须带**：
- **demo 边界**：一句话说清"做完能演示什么"（对 App 尤其顺——就是"卡片里能跑通什么交互"）。
- **验收点**：怎么知道这步成了。

**依赖排序**：用 `blockedBy` 声明步骤依赖（被依赖的先做），天然形成执行顺序。

**计划自检（适用于 T2）**：
- [ ] 每条需求至少映射到一个步骤
- [ ] 边界情况（异常、空输入、失败路径）在步骤里显式出现
- [ ] 单步不承载多个独立结果；步骤数由可独立验证的边界决定

**反合理化**：
| 借口 | 现实 |
|---|---|
| "这步就是大，拆不开" | 拆不开 = 你没找到边界。先写 demo 边界，边界自然逼出拆法 |
| "先做出来再补计划" | 那是 vibe coding 的坑，做完发现方向错，返工更贵 |

## §2 根因调试（阶段③，小检验失败时）

**调试原则**：修复前先收集足以定位问题的证据；调查深度随影响和复现难度调整，不因小而明确的修正强制完成全部阶段。

**四阶段（复杂或反复出现的问题按需使用）**：

**Phase 1 · 根因调查**
1. 完整读错误/堆栈，不跳过 warning（常含答案）
2. 稳定复现；复现不了就继续收集数据，**不许猜**
3. 查最近改动（diff / 依赖 / 配置 / 环境）
4. 多组件系统：在**每个组件边界**加诊断（进/出数据、配置传播），跑一次先定位是哪层断裂
5. 数据流反向追溯：坏值从哪来？一直追到源头，**修源头不修症状**

**Phase 2 · 模式分析**
- 在同项目找能跑的相似例子
- 对照参考实现要**逐行读完**，禁止略读后"adapt"
- 列出 working 与 broken 的**每一处**差异，多小都列

**Phase 3 · 单假设**
- 明确写出："我认为 X 是根因，因为 Y"
- 一次只动一个变量的最小测试
- 失败 → 提**新**假设，禁止在旧修复上叠加
- 不懂就说不懂

**Phase 4 · 实现**
- 先建失败复现（最简，没有框架就一次性脚本）
- 再做单一修复；禁止"顺手改进"、禁止捆绑重构

**止损信号**：多次有证据的修复仍失败、每次在别处引入新问题或修复范围持续扩大时，暂停补丁，重新审视假设、边界和设计；次数本身不能证明架构错误。

**Red Flags 自检**（出现任一条 = 回 Phase 1）：
- "先快速修了再查"
- 一次改多处一起跑测试
- 跳过测试手动验证
- "再试最后一次"

## §3 独立审查（阶段③，按风险启用）

**适用时**：对跨层、高风险、安全/数据敏感或用户要求审查的改动，优先安排独立审查；小改按风险自检即可。

**审查上下文保持聚焦**：
1. 让审查者评判**产物本身**，不被作者思路带偏、不产生共情
2. 保住作者自己的上下文窗口继续干活（子 Agent 上下文与主会话互不消耗）

**审查者至少拿到**：
- `DESCRIPTION`：做了什么
- `PLAN_OR_REQUIREMENTS`：应该做什么（指向计划文件）
- `BASE_SHA` / `HEAD_SHA`：产物/代码区间（精确框定范围）

**反馈分级处置**：
| 级别 | 处置 |
|---|---|
| Critical | 立即修 |
| Important | 修完才能进下一步 |
| Minor | 记录，稍后处理 |

审查者也可能错——可用技术理由 + 证据 push back，但**禁止与有效技术反馈争辩**。

**审查边界**：对跨层、高风险、数据/权限敏感或用户要求的工作安排独立审查；小改不为形式强制派审查。带未修的 Critical/Important 进入发布应明确记录并处理或取得用户接受。

## §4 代码原则清单（阶段④，清理优化）

按 P1–P10 逐维扫。对 Hana App（前端卡片类），**P2 / P5 / P6 / P9 权重最高**。

| # | 原则 | 一句话 |
|---|---|---|
| P1 | 正确性优先 | 能跑的代码 > 优雅的代码 |
| P2 | 可观测 | 错误必须可见、可记录、可追踪（反对静默失败、过宽 catch） |
| P3 | 非法状态不可表示 | 用类型/结构在源头消灭一类 bug |
| P4 | 单一职责 | 一个单元只干一件事 |
| P5 | 显式优于隐式 | 清晰胜过聪明（反对 magic value、隐藏依赖） |
| P6 | 最小暴露面 | YAGNI，只暴露必要的 |
| P7 | 有测试为证 | 优先用适合风险的测试；未覆盖项如实标记，不以文档/静态检查冒充运行时证据 |
| P8 | 安全演进 | 公开接口变更要给迁移路径 |
| P9 | 故障隔离 | 单个坏输入不该崩掉整个系统（超时/重试/资源泄漏） |
| P10 | 注释讲为什么 | 解释原因，不复述机制 |

**发现定级**：CRITICAL → HIGH → MEDIUM → LOW → INFO，按级排处置顺序。
**工作量标注**：S / M / L / XL。

**别丢 Strengths 段**：同时记录值得保留的好模式——防止优化把好味道也磨掉。

## §5 交付前自检（阶段⑤）

**本套东西自己就是 skill**，所以这条是给自己的规矩（吸收自 Qoder Writing-Skills）：

**目标**：尽量用行为评估校验规则是否改变了预期行为。无法运行独立基线/对拍时，如实标记未测；不得声称观察到 RED/GREEN。

TDD 映射：
| TDD | 写 skill |
|---|---|
| 测试用例 | 子 Agent 压力场景 |
| 生产代码 | SKILL.md 文档 |
| RED | 无该条文时 agent 违规（基线失败） |
| GREEN | 有该条文时 agent 合规 |
| REFACTOR | 保持合规前提下逐个堵漏洞 |

**最小化写作**：根据已观察到的失败或明确的高影响风险写最窄规则；评估记录区分实测、静态推演和待验证假设。

**抗合理化设计**：不只申规则，要逐条点名禁止具体绕行；前置"违反字面即违反精神"掐断整类辩解。

**App 代码产物部分**：按本次风险核对验收映射；仅在 §3 的适用条件成立时安排独立审查。没有审查资源时说明限制，不得把自查写成独立审查。

## §6 设计方法论（阶段①③）

> Hana App 的第一印象就是卡片长什么样。设计不是"做完再美化"，是从目标阶段就要定的方向。

**流程（ui-designer）**：参考 → 抽设计系统 → 明确需求 → 实现。中间产物（设计系统）的质量直接决定实现质量。

**设计系统骨架（逐项填满，别漏格）**：色板（主/次/强调/功能色）、字体（族/字号/字重/行高）、组件样式、间距刻度、动效、暗色变体。用**具体值**（hex/px），不用形容词。

**写码前四问（frontend-design）**：
- Purpose：解决什么问题、谁用
- Tone：选一个明确的美学方向
- Constraints：框架 / 性能 / 无障碍
- Differentiation：让人记住的那一个点

**反 AI 味清单（frontend-design）**：禁默认系统字体、禁"白底紫渐变"套路、禁每次生成都收敛到同一批安全选择。要有性格的 display 字体 + 精炼正文体；主导色 + 锋利强调色 > 平均分配。

**统一压倒丰富（stepfun-design）**：高级感来自统一，不是元素多。层级靠**排版尺度与留白**拉开，不靠色块和阴影。单品牌色 + 出现位置白名单。

**Token 三层（web-design-pro）**：Primitive（原始值）→ Semantic（语义角色）→ Component（组件专用）。设计决策变数据，设计-代码 gap 靠变量引用消除。→ Hana 里对应宿主注入的 `--hana-*` 变量链（见 capability-map §B1）。

**硬指标（可核对，别用形容词）**：对比度 ≥4.5:1；间距用统一刻度；纯图标按钮必有 `aria-label`；尊重 `prefers-reduced-motion`；图片声明尺寸防抖动。

**先发散再收敛（ui-designer）**：实现阶段先出多变体（如移动 3 版）→ 聚成一页对比 → 再定稿。

**视觉资产**：卡片图 / 封面用 SVG（矢量不糊）；技术示意图可参考 drafter 的"工程蓝图"风。

**动效选型（web-animation-design）**：可打断的交互（拖拽/手势）必须用 spring，不用 CSS 动画（CSS 被打断会从零重启，spring 保留速度）；**动效先于布局**——设计界面前就决定元素靠 shared morph 还是出现/消失，位置要为转场留通道。

**分层交付（figma-design-analyzer）**：同一数据按消费者分格式——机器用 JSON、评审用可视化报告、执行期用图片资源。设计基准类产物照此分层。

**图例先立（drafter）**：符号语义固定成图例（虚线=抽象关系、单色=克制、等宽=数据），再画图。可复用 CSS 片段打包进 skill，不靠现场生成。

## §7 架构与决策（阶段②④）

**三模式（architecting）**：动手前先分叉——DESIGN（从 0 到 1）/ EXTEND（在已有上加）/ BUILD（照既定方案实现）。三者流程与产出物不同。

**动手前存在性检查**：先读已有结构，避免重复造轮子。

**该不该拆的硬阈值（KISS）**：文件数少于 3 个就并入，不单开目录。这是"什么时候该拆"的可量化判据。

**分层顺序（防耦合）**：L1 纯逻辑（不碰 UI）→ L2 组件（不含业务逻辑）→ L3 页面 / 集成；**类型先行**。→ 对应 Hana App：`lib/`（纯逻辑，可单测）→ `index.js`（宿主编排）→ `ui/`（卡片）。

**拒绝清单（质量底线）**：循环依赖、滥用全局状态、`any` 类型、无注释的关键逻辑。

**ADR 四段（architecture-documenter）**：Context（现状+问题）→ Decision（含实现细节）→ Alternatives（每个方案 pros/cons + 拒绝理由）→ Consequences（正/负影响 + 缓解）。大决策再加风险表、回滚方案、成功指标。

**记录"为什么"**，不只"是什么"；过期文档**归档而非删除**；文档与代码同版本。

**决策顺序（api-scaffolding）**：需求 → 边界 → 契约 → 通信 → 韧性 → 可观测 → 安全 → 性能 → 测试 → 文档。**先边界后契约；韧性与可观测在实现前设计，不是事后补。**

**先问非功能需求**：规模、延迟、一致性——很多流程缺这一问。

## §8 版本与沉淀（阶段③⑤）

**提交规范（git-commit）**：仅在用户明确要求 commit 时使用；`<type>[scope]: 描述`、命令式和破坏性变更标记可作为提交约定，具体以仓库规范为准。

**一次提交一个主题**：获准提交时按逻辑分组，不把无关改动混在一起。提交是可选的检查点，不是每个小检验单元的强制产物。

**提交范围**：开始前查看 `git status` 和相关 diff；只暂存本次路径，再检查 `git diff --cached`。已有改动、未跟踪文件或敏感内容不因一次 commit 请求而自动纳入。

**双轨语言（git-commit）**：对用户只用大白话（"存档"/"回到之前某个存档"），内部保留规范术语，术语首次出现时解释。

**Git 作为范围与恢复证据（阶段③④⑤ 按需使用）**：

Git 可用于检查改动范围、建立恢复点和标记发布版本；各动作按任务需要和用户授权执行：

| 阶段 | 动作 | 它产出什么证据 |
|---|---|---|
| ③ | 按需查看 `git diff`；用户要求 commit 时建立检查点 | 变更范围与可回退提交；提交不是验收的替代品 |
| ④ | 记录优化前后基线，重跑相关检查；获准提交时才建检查点 | 差异范围和实际回归结果；diff 本身不能证明行为不变 |
| ⑤ | 用户授权后按目标执行 push、tag、Release 等动作 | 对端状态与附件回读，证明确实发布到预期位置 |

**“行为不变”要由相关验收支持**：差异能显示改动范围，但不能单独证明功能与样式没有回归。

**如实报告已执行的 Git 动作**：简要给出命令或目标和实际结果；没有执行提交或发布时，不写成已完成：

```
git commit -m "feat(panel): 五标签重构"   → a1b2c3d
git diff v0.2.0..v0.3.0 --stat           → 6 files, +412 -198
```

**历史纪律**：

| | 放哪 | 留多少 |
|---|---|---|
| 开发提交 | 依仓库协作约定 | 依仓库协作约定 |
| 版本提交 | 默认分支 | 不要求与版本数相等 |
| 标签 | tag | 每个 release 一张 |

不要为了固定提交数擅自 squash、改写历史或重建默认分支。已公开历史不可改写；历史整理或其他可能影响协作者的操作，遵守项目规范并先明确授权目标。

**发布计划的授权边界**：push、创建/推送 tag、公开 Release、市场 PR 是不同的对外动作。用户可一次授权一份完整列明动作和目标的计划；仓库、分支/修订、版本、附件或 PR 目标变化后重新确认。目标能从项目上下文可靠确定时不重复追问；无法确定且会改变发布结果时，只询问缺失信息。完整授权的发布顺序遵守项目现行流程；Hana 市场投稿另见 `references/market-enrollment.md`。

**经验沉淀触发清单（self-improving-agent）**：6 种情况当场记——操作失败、被用户纠正、用户要新能力、外部服务异常、知识过时、发现更优流程。不靠自觉。

**条目必须含"下次该做什么"**：明文禁止"再看看"式记录。

**三层晋升**：pending → resolved → promoted；同类问题重复三次即晋升为长期规则，原条目注明去向。

**信息组织三步（ppt-visual-designer）**：降维（长句压成 3–5 个关键词）→ 找飞轮（识别循环逻辑）→ 建对比（凡涉及变革必设 Before/After）。→ 用于 README、说明卡、方案文档。

## §9 反合理化总表（贯穿全程）

> 想跳过某步时，先查这里。多数"这次特殊"都是幻觉。

| 借口 | 现实 |
|---|---|
| "就一个 quick fix，先修了再说" | 越急越要走流程；systematic 比瞎试快 |
| "问题看起来很简单" | 简单的 bug 也有根因 |
| "时间紧，跳过必要的对齐" | 对会改变行为、安全、数据或外部副作用的未决事项，先厘清再动手；简单任务不强制写计划 |
| "太简单不用审查" | 按跨层程度、影响与用户要求决定；小改可不做独立审查 |
| "我已经试过好几个修复了" | 那正是该停下来查根因的信号 |
| "这次情况特殊" | 先证明它特殊，再谈例外 |
| "先写出来再补测试/验收" | 未测 = 未验证 |

**按意图执行流程**：不可跳过本任务必要的安全与验证边界；与本任务无关的步骤不因流程字面而强行执行。

### 已有产物的发布收敛

当实现与验收已经存在，用户只要求打包、上传、推送或更新市场时：

1. 复用已有验收证据；不重做需求、设计或全量测试，只补本次打包与发布新增的风险检查。
2. 按“组装一次 → 一处完整性检查 → 发布一次 → 目标回读”完成；先核对目标位置已有文件、Release、市场登记与更新方向。
3. 发布命令失败时先读完整报错并修正根因；同类失败最多主动修正一次，第二次失败就报告已成功部分、卡点和下一步，不再连续尝试等价命令。这条限制只约束打包、上传、推送、Release 和市场登记，不替代实现与排障的换路条件。
4. 目标侧已回读成功就停止，不把“再确认一下”执行成重复发布。

## §10 对话纪律（贯穿阶段①③）

> 脚手架管流程，这一节管协作姿势。它们是轻量提示，不要求每次都多一轮确认；遇到明确简单的任务，直接做并验证。

1. **一条消息一个主要任务**：若有并列事项，先标明优先级与依赖，避免模型自行猜重点。
2. **说完成定义，不预设实现手段**：说明用户可观察的结果和边界；技术方案由实现者结合仓库现状选择。
3. **验收先行，改完必验**：动手前明确怎么算完成；改完运行相应检查并报告证据，不用过程汇报代替验证。
4. **一次只验证一个主要变量**：调试时让因果关系清晰；不要把多个假设或顺手重构捆在一次尝试里。
5. **复杂任务先预演**：先简述目标、主要文件/模块、实现路径与验证方式；对有取舍的工作先给短计划，简单任务免仪式。
6. **反复纠正仍无进展就重置思路**：若同一问题多次纠正仍偏离，停止堆叠失败路径，重新核对需求与证据；必要时总结状态后开新会话续做。

**迁移说明**：以上纪律适用于代码协作；“复杂”按风险和跨层范围判断，不以固定文件数/轮数机械触发。push、部署、发布、生产数据操作等外部动作仍须另行明确授权。

## §11 省思考六招（贯穿全程）

> 一句话：**能用规矩的，不想；能用程序的，不想；能抄的，不想；能问别人的，不想。**
> 触发信号：你已经在“再多想想”上花的时间超过了动手时间，或任务明明很简单、模型却在反复自查。

### 招 1 · 规则写动作，不写原则

- 坏：「改文件要注意细节、要谨慎、别出错」——模型会把“谨慎”执行成每改一行翻一遍全项目。
- 好：「改文件前只备份这一个文件 → 备份完直接改 → 不再确认」。
- 写法：`遇到 <具体情形> → 直接做 <具体动作>`；一条规则只对应一个可观察动作。
- 允许写“自动开关”：明确规定走到哪一步自动触发、哪一步不许触发，避免每一步都停下来判断要不要做。

### 招 2 · 能程序判定的，不交给模型

- 存在性、格式、计数、加总、一致性、漏没漏，一律写脚本一次判定。
- 模型数数会数漏、比分会看走眼，还烧 token；脚本一秒出结果且零误判。
- 本 skill 的 `scripts/check_app.mjs` 就是这条的落地：坑从文档变门禁。没有现成脚本时，先问“这判断能不能写成十行脚本”，能就先写。

### 招 3 · 能抄的，不让他自己想

- 遇问题先找现成实现与参考，别从零琢磨出一个四不像。
- 顺序：仓库内已有实现 → 官方示例 → GitHub 同类项目 → 都没有再自己写。
- 抄的是**结构与做法**，不是成段搬来源不明或许可证不清的代码；抄完仍按本项目契约改写并验证。

### 招 4 · 查问题的顺序倒过来

- 顺序：**社交媒体 → 社区/论坛 → GitHub Issues → 官方文档（最后）**。
- 理由：官方文档写“应该怎样”，社交媒体和 Issues 写“今天实际出了什么事”。新版本刚出的坑，官网还没更新，用户已经骂了三天，绕过办法也贴出来了。
- 适用：版本更新后功能突然不好使、报错信息很新、官方文档与实测不符。
- 仍要交叉验证：社区说法与官方契约冲突时，以能复现的实测为准；查到的办法要落到本仓库验证一次。

### 招 5 · 思考方式强制触发，不说“多想想”

“多想想”等于想更多，通常更慢更差。改成触发条件绑固定动作：

| 触发 | 强制动作 |
|---|---|
| 同一个错卡了 2 次 | 停止打补丁 → 先最小复现 → 换假设方向 |
| 改动跨 2 层以上（UI/逻辑/存储/网络） | 先画数据流与边界 → 再动手 |
| 有 2 个以上合理方案 | 列选项与代价 → 用户拍板，不自己闷头选 |
| 实现已验收，只需打包/上传/更新市场 | 复用证据 → 组装一次 → 一处完整性检查 → 发布一次 → 目标回读 |

目的不是想更久，是想对地方。

### 招 6 · 拿不准就叫另一个 Agent 对撞

- 一个模型自己检查自己，就像自己批改作业，错的地方永远觉得对。
- 做法：一个当**红队**专挑毛病（找反例、找边界、找会炸的地方），一个当**蓝队**守方案（解释为什么这样设计）；对完再定。
- Hana 里用子 Agent 做红队；没有独立资源时如实说“未做独立复核”，不把自查说成互检。

**六招的共同点**：把“让模型判断”换成“给定条件 + 固定动作”。省下的不只是 token，是它反复自我确认的时间。

**边界**：这六招治的是“想太多”，不是“不验证”。安全、数据、权限、外部动作的验证一条都不能省；省掉的是重复确认与无效思考。
