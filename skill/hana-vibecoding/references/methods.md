## §1 计划拆分标准（阶段②）

**目标**：把需求拆成"小而一定做得完"的步骤。

**铁律**：**每个步骤必须 fits-one-run**——一次能做完、只承载一个可演示的结果。

**五条强制再拆触发条件**（命中任一就拆）：
1. 覆盖多个可演示结果
2. 跨多个不相关领域 / 模块
3. 缺清晰的验收边界
4. 含多个大阶段
5. 任务数超过 5~7 个

**每条步骤必须带**：
- **demo 边界**：一句话说清"做完能演示什么"（对 App 尤其顺——就是"卡片里能跑通什么交互"）。
- **验收点**：怎么知道这步成了。

**依赖排序**：用 `blockedBy` 声明步骤依赖（被依赖的先做），天然形成执行顺序。

**出口校验（不达标不进阶段③）**：
- [ ] 每条需求至少映射到一个步骤
- [ ] 边界情况（异常、空输入、失败路径）在步骤里显式出现
- [ ] 没有"多结果 / 超 7 任务"的步骤

**反合理化**：
| 借口 | 现实 |
|---|---|
| "这步就是大，拆不开" | 拆不开 = 你没找到边界。先写 demo 边界，边界自然逼出拆法 |
| "先做出来再补计划" | 那是 vibe coding 的坑，做完发现方向错，返工更贵 |

## §2 根因调试（阶段③，小检验失败时）

**铁律**：**NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST**——没完成根因调查，不许改代码。

**四阶段（每阶段完成才进下一阶段）**：

**Phase 1 · 根因调查**
1. 完整读错误/堆栈，不跳过 warning（常含答案）
2. 稳定复现；复现不了就继续收集数据，**不许猜**
3. 查最近改动（diff / 依赖 / 配置 / 环境）
4. 多组件系统：在**每个组件边界**加诊断（进/出数据、配置传播），跑一次先定位是哪层断裂
5. 数据流反向追溯：坏值从哪来？一直追到源头，**修源头不修症状**

**Phase 2 · 模式分析**
- 在同项目找能跑的相似例子
- 对照参考实现要**逐行读完**，禁止略读后"adapt"
- 列出 working 与 broken 的**每一处**差异，多小都列

**Phase 3 · 单假设**
- 明确写出："我认为 X 是根因，因为 Y"
- 一次只动一个变量的最小测试
- 失败 → 提**新**假设，禁止在旧修复上叠加
- 不懂就说不懂

**Phase 4 · 实现**
- 先建失败复现（最简，没有框架就一次性脚本）
- 再做单一修复；禁止"顺手改进"、禁止捆绑重构

**换层信号（与人格「止损」对齐）**：
- 失败 < 3 次 → 带新信息回 Phase 1
- 失败 ≥ 3 次 → **停止**。这不再是假设错，是**架构/设计错**（症状：每次修复在别处冒出新问题、每次都要大改）。跟用户讨论设计后再动第 4 次。

**Red Flags 自检**（出现任一条 = 回 Phase 1）：
- "先快速修了再查"
- 一次改多处一起跑测试
- 跳过测试手动验证
- "再试最后一次"

## §3 无偏审查（阶段③，较大步骤完成后）

**核心**：派**全新的**审查子 Agent 来验收，而不是自己看一遍。

**为什么不给会话历史（双重）**：
1. 让审查者评判**产物本身**，不被作者思路带偏、不产生共情
2. 保住作者自己的上下文窗口继续干活（子 Agent 上下文与主会话互不消耗）

**审查者只拿四件套**：
- `DESCRIPTION`：做了什么
- `PLAN_OR_REQUIREMENTS`：应该做什么（指向计划文件）
- `BASE_SHA` / `HEAD_SHA`：产物/代码区间（精确框定范围）

**反馈分级处置**：
| 级别 | 处置 |
|---|---|
| Critical | 立即修 |
| Important | 修完才能进下一步 |
| Minor | 记录，稍后处理 |

审查者也可能错——可用技术理由 + 证据 push back，但**禁止与有效技术反馈争辩**。

**红旗**："太简单不用审"永远禁止；带未修的 Important 继续推进 = 违规。

## §4 代码原则清单（阶段④，清理优化）

按 P1–P10 逐维扫。对 Hana App（前端卡片类），**P2 / P5 / P6 / P9 权重最高**。

| # | 原则 | 一句话 |
|---|---|---|
| P1 | 正确性优先 | 能跑的代码 > 优雅的代码 |
| P2 | 可观测 | 错误必须可见、可记录、可追踪（反对静默失败、过宽 catch） |
| P3 | 非法状态不可表示 | 用类型/结构在源头消灭一类 bug |
| P4 | 单一职责 | 一个单元只干一件事 |
| P5 | 显式优于隐式 | 清晰胜过聪明（反对 magic value、隐藏依赖） |
| P6 | 最小暴露面 | YAGNI，只暴露必要的 |
| P7 | 有测试为证 | 未测 = 未验证，没有例外 |
| P8 | 安全演进 | 公开接口变更要给迁移路径 |
| P9 | 故障隔离 | 单个坏输入不该崩掉整个系统（超时/重试/资源泄漏） |
| P10 | 注释讲为什么 | 解释原因，不复述机制 |

**发现定级**：CRITICAL → HIGH → MEDIUM → LOW → INFO，按级排处置顺序。
**工作量标注**：S / M / L / XL。

**别丢 Strengths 段**：同时记录值得保留的好模式——防止优化把好味道也磨掉。

## §5 交付前自检（阶段⑤）

**本套东西自己就是 skill**，所以这条是给自己的规矩（吸收自 Qoder Writing-Skills）：

**铁律**：**没有失败的基线测试，不写/不改 skill 条文。** 编辑已有条文同样适用。

TDD 映射：
| TDD | 写 skill |
|---|---|
| 测试用例 | 子 Agent 压力场景 |
| 生产代码 | SKILL.md 文档 |
| RED | 无该条文时 agent 违规（基线失败） |
| GREEN | 有该条文时 agent 合规 |
| REFACTOR | 保持合规前提下逐个堵漏洞 |

**最小化写作**：GREEN 阶段只针对**实际观察到**的违规写条文，不为假想情况加内容。

**抗合理化设计**：不只申规则，要逐条点名禁止具体绕行；前置"违反字面即违反精神"掐断整类辩解。

**App 代码产物部分**：退一级——交付前至少过一遍 §1 的验收映射 + §3 的 fresh reviewer。

## §6 设计方法论（阶段①③）

> Hana App 的第一印象就是卡片长什么样。设计不是"做完再美化"，是从目标阶段就要定的方向。

**流程（ui-designer）**：参考 → 抽设计系统 → 明确需求 → 实现。中间产物（设计系统）的质量直接决定实现质量。

**设计系统骨架（逐项填满，别漏格）**：色板（主/次/强调/功能色）、字体（族/字号/字重/行高）、组件样式、间距刻度、动效、暗色变体。用**具体值**（hex/px），不用形容词。

**写码前四问（frontend-design）**：
- Purpose：解决什么问题、谁用
- Tone：选一个明确的美学方向
- Constraints：框架 / 性能 / 无障碍
- Differentiation：让人记住的那一个点

**反 AI 味清单（frontend-design）**：禁默认系统字体、禁"白底紫渐变"套路、禁每次生成都收敛到同一批安全选择。要有性格的 display 字体 + 精炼正文体；主导色 + 锋利强调色 > 平均分配。

**统一压倒丰富（stepfun-design）**：高级感来自统一，不是元素多。层级靠**排版尺度与留白**拉开，不靠色块和阴影。单品牌色 + 出现位置白名单。

**Token 三层（web-design-pro）**：Primitive（原始值）→ Semantic（语义角色）→ Component（组件专用）。设计决策变数据，设计-代码 gap 靠变量引用消除。→ Hana 里对应宿主注入的 `--hana-*` 变量链（见 capability-map §B1）。

**硬指标（可核对，别用形容词）**：对比度 ≥4.5:1；间距用统一刻度；纯图标按钮必有 `aria-label`；尊重 `prefers-reduced-motion`；图片声明尺寸防抖动。

**先发散再收敛（ui-designer）**：实现阶段先出多变体（如移动 3 版）→ 聚成一页对比 → 再定稿。

**视觉资产**：卡片图 / 封面用 SVG（矢量不糊）；技术示意图可参考 drafter 的"工程蓝图"风。

**动效选型（web-animation-design）**：可打断的交互（拖拽/手势）必须用 spring，不用 CSS 动画（CSS 被打断会从零重启，spring 保留速度）；**动效先于布局**——设计界面前就决定元素靠 shared morph 还是出现/消失，位置要为转场留通道。

**分层交付（figma-design-analyzer）**：同一数据按消费者分格式——机器用 JSON、评审用可视化报告、执行期用图片资源。设计基准类产物照此分层。

**图例先立（drafter）**：符号语义固定成图例（虚线=抽象关系、单色=克制、等宽=数据），再画图。可复用 CSS 片段打包进 skill，不靠现场生成。

## §7 架构与决策（阶段②④）

**三模式（architecting）**：动手前先分叉——DESIGN（从 0 到 1）/ EXTEND（在已有上加）/ BUILD（照既定方案实现）。三者流程与产出物不同。

**动手前存在性检查**：先读已有结构，避免重复造轮子。

**该不该拆的硬阈值（KISS）**：文件数少于 3 个就并入，不单开目录。这是"什么时候该拆"的可量化判据。

**分层顺序（防耦合）**：L1 纯逻辑（不碰 UI）→ L2 组件（不含业务逻辑）→ L3 页面 / 集成；**类型先行**。→ 对应 Hana App：`lib/`（纯逻辑，可单测）→ `index.js`（宿主编排）→ `ui/`（卡片）。

**拒绝清单（质量底线）**：循环依赖、滥用全局状态、`any` 类型、无注释的关键逻辑。

**ADR 四段（architecture-documenter）**：Context（现状+问题）→ Decision（含实现细节）→ Alternatives（每个方案 pros/cons + 拒绝理由）→ Consequences（正/负影响 + 缓解）。大决策再加风险表、回滚方案、成功指标。

**记录"为什么"**，不只"是什么"；过期文档**归档而非删除**；文档与代码同版本。

**决策顺序（api-scaffolding）**：需求 → 边界 → 契约 → 通信 → 韧性 → 可观测 → 安全 → 性能 → 测试 → 文档。**先边界后契约；韧性与可观测在实现前设计，不是事后补。**

**先问非功能需求**：规模、延迟、一致性——很多流程缺这一问。

## §8 版本与沉淀（阶段③⑤）

**提交规范（git-commit）**：`<type>[scope]: 描述`，描述 ≤72 字符、命令式；破坏性变更加 `!` 或 `BREAKING CHANGE:` 脚注。→ 可直接用作每步产物的版本说明格式。

**一次提交一个主题**：按逻辑分组，不把无关改动混在一起。对应"每个小检验单元只做一件事"。

**提交前确认门**：展示"会存哪几个文件、说明写什么"再动手；用户已明确要求则免二次确认。

**双轨语言（git-commit）**：对用户只用大白话（"存档"/"回到之前某个存档"），内部保留规范术语，术语首次出现时解释。

**Git 当证据机（阶段③④⑤ 三处用法）**：

git 在这套流程里有三个不可替代的用途，都不只是"存个档"：

| 阶段 | 动作 | 它产出什么证据 |
|---|---|---|
| ③ | 每个小检验通过 → 一次 commit | 一个可回退的检查点；`git diff --stat` 就是改动清单，不用手写 |
| ④ | 优化**前后各一次** commit | `git diff 前..后` 证明"只动了这些、功能与样式没变" |
| ⑤ | `push → tag → push --tags → release` | tag 把"发布了哪个版本"钉死在具体提交上 |

**为什么④必须要前后两次提交**："优化后功能不变"这句话，没有 diff 就是空口断言。有了 diff，评审者能自己看改动范围——这是可验证，不是可信任。

**回复标注硬要求**：凡用到 git，回复里必须给出**命令 + `→` 结果**，不能只说"我提交了"：

```
git commit -m "feat(panel): 五标签重构"   → a1b2c3d
git diff v0.2.0..v0.3.0 --stat           → 6 files, +412 -198
```

**历史纪律（发布后清理）**：

| | 放哪 | 留多少 |
|---|---|---|
| 开发碎步提交 | 本地 / `dev` 分支 | 不限，发完可丢 |
| 版本提交 | `main` | **= 版本数** |
| 标签 | tag | 每个 release 一张 |

发版时把碎提交 **squash 成一次**提交进 `main`，再打 tag。`main` 永远是一条干净版本线。

两条红线：
1. **已公开的仓库不改写历史**——别人可能已克隆，改写会让他们的库对不上。
2. 真要瘦身只能用"重新起根"（`git checkout --orphan`），且**只在确认没人依赖旧提交时**才做。

**顺序铁律**：`push → tag → push --tags → release`。反例：tag 打在旧提交上（曾踩）。

**经验沉淀触发清单（self-improving-agent）**：6 种情况当场记——操作失败、被用户纠正、用户要新能力、外部服务异常、知识过时、发现更优流程。不靠自觉。

**条目必须含"下次该做什么"**：明文禁止"再看看"式记录。

**三层晋升**：pending → resolved → promoted；同类问题重复三次即晋升为长期规则，原条目注明去向。

**信息组织三步（ppt-visual-designer）**：降维（长句压成 3–5 个关键词）→ 找飞轮（识别循环逻辑）→ 建对比（凡涉及变革必设 Before/After）。→ 用于 README、说明卡、方案文档。

## §9 反合理化总表（贯穿全程）

> 想跳过某步时，先查这里。多数"这次特殊"都是幻觉。

| 借口 | 现实 |
|---|---|
| "就一个 quick fix，先修了再说" | 越急越要走流程；systematic 比瞎试快 |
| "问题看起来很简单" | 简单的 bug 也有根因 |
| "时间紧，跳过计划" | 方向错返工更贵 |
| "太简单不用审查" | 永远禁止 |
| "我已经试过好几个修复了" | 那正是该停下来查根因的信号 |
| "这次情况特殊" | 先证明它特殊，再谈例外 |
| "先写出来再补测试/验收" | 未测 = 未验证 |

**违反流程字面 = 违反流程精神。** 不许用"我按精神办事"绕行。
