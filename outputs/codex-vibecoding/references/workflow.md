# 从需求到交付的工作流

按风险取用，不要求每个请求产生计划书。T0 用最短闭环；T2 使用下面的全链路，某环节不相关时明确略过。

## 0. 看清现场

- 找到仓库根、适用的 `AGENTS.md`、README、架构/开发文档和相关入口；不要仅凭目录名猜技术栈。
- 看 `git status` 与相关 diff。区分本次改动与用户已有修改；不覆盖、清理或改写无关内容。
- 检查现有脚本、测试、CI、部署目标、锁文件、数据 schema 与设计系统。优先用项目已提供的检查命令。
- 读取仓库中与当前框架/API 精确匹配的文档；框架版本不同，不套用记忆中的旧 API。
- 遇到具体故障先收集证据：完整错误、版本、复现步骤和最近变化。查近期社区/issue 报告获取线索，再用 GitHub 源码、release notes 和官方文档确认根因与适用条件；不要把社交媒体上的绕过方式直接当结论。
- 文件数量、引用关系、schema 一致性等机械事实优先用 `rg`/脚本/测试确认；不要靠模型逐个阅读计数。

## 1. 定义结果与边界

把“做完”写成可观察行为，而非预设实现：谁使用、从哪里进入、输入/输出是什么、关键状态如何变化。标明不做什么、兼容性要求和非功能约束（隐私、安全、无障碍、性能、成本、设备）。

仅在缺失信息会改变用户可见行为、数据安全/迁移、认证策略、付费/外部副作用时提问；其余用仓库现状作最小假设并披露。多模块工作使用 `templates/brief.md`，小任务只需在对话中简要列出验收点。

## 2. 探索与设计方案

- 先找仓库内已有实现和项目依赖的现成能力；能复用就复用，不能复用时说明缺什么，再设计最小新增。
- 追踪真实调用路径：页面/组件 → 请求边界 → 服务/领域逻辑 → 数据或外部系统；确认错误和状态返回到 UI 的路径。
- 用现有模式解决，不先造框架。明确职责与边界、关键依赖、权限/信任边界、失败恢复方式。
- 对新 UI 先选一个具体视觉方向和信息层级；按目标用户检查首屏、空/错/加载/成功状态、窄屏与键盘使用。复用项目 token/组件，禁止无意引入另一套视觉系统。
- 数据与 API 先定契约：实体/关系、必填与唯一约束、分页/排序/过滤、验证位置、错误语义、版本兼容、权限与所有权。避免只做前端假数据而把集成说成完成。
- 写短计划并按依赖排序：每项应有可演示结果和验证方式；能独立完成的垂直切片优先。没有明确收益不要拆出额外 package/service。

## 3. 逐片实现

每片纵向穿过必要的 UI、API、业务规则与持久化，并展示一个可验证结果。定义并保持模块边界：展示逻辑留在 UI，输入校验和授权在可信服务端，数据库访问不暴露到客户端，跨层契约有共享类型或可验证 schema。

实现前先用一次窄范围检索确认没有可直接复用的同类代码；发现现成模式时优先适配，避免为了“原创”引入第二套做法。

行为新增/修复时，优先为关键行为先写或补回归测试，再运行确认测试能抓到预期差异；随后实现最小改动并重跑。对无法合理自动化的视觉或真实外部行为，安排可复现的手动步骤。不要为纯文案、生成文件或一次性原型强加完整 TDD 仪式。

异常必须可观察：返回有用且不泄漏秘密的错误，记录必要上下文，不吞异常；超时、重试、幂等、并发控制只按场景需要设计，并界定副作用。

## 4. 测试与验收

从最便宜且最接近风险的检查开始：相关单测/组件测试 → API/数据库集成测试 → 关键端到端用户路径 → lint/类型检查/构建。选择覆盖风险的子集，而不是为清单打勾跑无关矩阵。

- 能用程序判断的验收项优先写成脚本/测试；不要让模型手工扫描大量文件来证明数量、格式或引用完整。
- 测正常路径，也测边界与失败：无效输入、未授权/跨用户、空值、重复请求、网络/依赖错误、分页边界、过期状态等，仅包含本功能相关项。
- 用项目的真实命令执行检查；读完整输出、确认退出码。修复检查中发现的问题后重跑受影响检查。
- UI 在可用浏览器里操作关键流程，核对实际布局、窄视口、焦点/键盘、错误与加载状态；能截图时用实际截图，不以代码读起来正确代替视觉验收。
- 若依赖真实服务但当前无凭证/网络/环境，标记未验证；不伪造成功响应或把 mock 说成生产集成。

## 5. 安全、可维护性与性能

按 [全栈检查表](fullstack-checklist.md) 选相应项。功能实现期间落实基础安全；出现认证、敏感数据、文件上传、支付或公开端点时扩大检查并查 OWASP/框架官方当前文档。专项审计、渗透测试与合规结论不因做过普通代码检查而成立。

测试过后复核 diff：是否超出范围、增加不必要依赖、遗留调试代码/密钥、前后端契约不一致、错误处理过宽、文档与实现冲突。按改动风险做独立审查，不为小修强制派审查流程。

## 6. 交付与线上操作

按 `templates/delivery.md` 汇报目标覆盖、重要改动、实际验证命令/结果、限制与风险。核对最终 diff 和工作区状态。

部署与运维也是全栈完成链的一部分，但**部署方案/说明**和**执行部署**是两件事：

- 设计与文档按项目平台说明构建命令、运行时版本、环境变量名称（不写 secret 值）、域名/路由、数据库依赖、健康检查、日志/告警与回滚路径。
- 准备环境区分 preview/staging/production；列出密钥配置、权限最小化、CI 检查和部署顺序。生产 migration 核查旧/新代码兼容、备份、锁/长事务风险及恢复策略；必要时采用 expand → backfill → contract。
- 执行前核实目标项目/环境/域名、版本、差异、迁移影响与用户授权。部署后检查实际版本、服务健康、日志/告警及关键用户路径；目标侧回读后才报告“已上线”。失败时先按已确认的回滚/止损方案处理。

本地构建通过不等于部署成功。生产部署、push、公开发布、线上写数据、不可逆迁移、清理数据或付费动作不从“帮我实现功能”推断授权；未授权时交付经过验证的代码与清楚的执行说明。
