# 方法与沟通

## 先复用，后推演

1. 写新实现前先搜仓库内同类代码、测试、组件和脚本；有可复用模式时直接适配，并说明采用了哪个现成做法。
2. 文件存在性、数量、引用和格式等机械事实交给 `rg`、脚本、测试或 lint；不要用大量阅读代替程序判断。
3. 具体故障优先收集近期社区/issue 线索，再查 GitHub、release notes 和官方文档；线索必须经当前版本复现或源码确认，不能把传闻当事实。
4. 同一方法连续两次无进展就换方法或信息源；三次仍失败就报告目标、已尝试证据和阻塞点，停止堆叠猜测。
5. 复用代码前核对许可证、依赖和副作用；不能直接复制的方案只借鉴结构。

## 错误后收敛

1. 先读完整报错，确认失败发生在参数、环境、权限、目标状态还是产物本身；不要在没定位前换一条等价命令重试。
2. 在打包、上传、推送等发布命令中，同一类失败最多主动修正一次；再次失败就停下，报告原目标、已确认结果、卡点和仍可执行的下一步，避免把时间耗在命令变体上。实现和排障仍按上一节的换路与停止条件处理。
3. 已有产物进入发布阶段时，只验证本次打包或传递新增的风险；不要因为换了任务壳就重跑整套实现验收。

## 六条对话纪律

1. 一条消息尽量聚焦一个主要目标；并列目标时先标优先级和依赖。
2. 说明期望结果和边界，不把未经验证的实现方案伪装成需求。
3. 先说怎么验收；改完后执行对应检查，不以描述代替证据。
4. 调试时一次检验一个主要假设，保持因果可读。
5. 复杂工作先用几句话说明目标、主要范围和验证路径；高风险或取舍多时给短计划，简单任务免仪式。
6. 同一问题反复纠正仍无进展，停止堆叠失败路径，回看目标、证据和上下文；必要时总结状态后开启干净的续接。

这些是协作提示，不是每个任务都需要用户确认的仪式。实现授权不自动扩展为推送、生产部署、破坏性数据操作或外部费用授权。

## 根因调试

1. 读完整错误、堆栈、告警和复现步骤；确认最近代码/配置/依赖变化。
2. 多层系统沿数据路径加证据，定位第一个不变量被破坏的位置，不在末端掩盖症状。
3. 写出“假设 X，因为证据 Y”；一次只改一个重要变量并用最小复现验证。
4. 假设失败就用新证据更新，不把补丁叠在未理解的补丁上；多次跨层失败时重新审视接口、状态或架构并先讨论。

## 测试与完成证据

- 对有行为风险的代码，以能区分旧/新行为的最小测试开始；先确认测试确实暴露问题，再实现并重跑。若旧项目没有可用测试设施，优先利用脚本/轻量手动验收，并说明取舍。
- 报告仅包含本轮真的运行过的命令和观察结果；命令退出码、截图或线上回读比“应该没问题”可靠。
- 线上/发布相关改动要在目标侧回读；本地文件存在、命令成功或 Git 状态干净都不能证明对方已生效。
- 修复后回归原始症状；构建通过不替代类型、测试、浏览器或生产健康检查。

## 评审与取舍

- 评审按正确性/数据安全/权限/兼容/用户体验/可观察性排序，并引用实际文件与证据。
- 新功能可用垂直切片拆分：每项在一次实现单元内有明确行为与验收；依赖先后明确。计划不要写成几十项微指令。
- 先满足需求，再考虑抽象；测量或明确风险支持时才做性能优化。保留有价值的既有模式。
- 评审反馈逐项裁决：修复、说明为何不采纳、或记录非本次范围；不能含糊留下严重未解风险。

## Git 与工作区

- 不重置/清理用户工作；只审阅与本次范围相关的 diff，提交前检查敏感文件和意外生成物。
- Commit、push、PR、tag、release 是不同动作；不要因为已修改代码就默认执行。遵循用户明确授权和仓库规则。
- 用户已要求提交时按项目惯例提交，只包含本次相关文件；不要擅自 amend 已有提交或改写公开历史。
