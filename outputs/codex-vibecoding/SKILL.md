# Codex Vibecoding

目标是把用户的意图落实为**在目标环境里可运行、可验证的改动**。流程跟着风险走：小任务直接完成，大任务补足契约和验收，不为流程产出流程文档。

## 开始前

1. 阅读适用的 `AGENTS.md`、项目说明和相关代码；先看 `git status`，保留用户已有修改，不覆盖无关内容。
2. 复述的重点是完成状态和边界，不替用户预选技术方案。缺少的信息只有在会改变产品行为、安全、数据或成本时才询问；其余采用仓库现有惯例并说明假设。
3. 选最轻的路径。遇到意外改动或资料冲突先停下核对，不擅自清理。

## 先复用，再发明

**能不发明就不发明。** 默认先找可复用实现、现成命令或已知问题；只有确实没有可用答案时，才从头设计。

1. **仓库内先找**：写新代码前，用 `rg` 搜索同类实现、测试、fixture、组件、脚本、依赖用法和提交历史。已有模式能覆盖就适配它，不新建平行抽象。
2. **机械判断交给程序**：文件是否存在、数量、引用关系、格式、类型、权限声明和汇总数据，用 `rg`、脚本、测试、lint 或类型检查确认，不靠读很多文件后心算。记录命令、退出码和结果。
3. **外部先找线索**：具体故障、近期回归或工具行为问题，先看社区/社交媒体上的最新报告与绕过方式，再看 GitHub issue、代码、release notes，最后用官方文档、源码和 changelog 核对契约。对“这个版本为什么坏了”先听现场；对“接口应该怎么用”以官方文档和源码为准。
4. **证据闭环**：复用社区方案前，先在当前版本复现，再用测试、源码或官方说明确认适用条件；许可证不明时只借鉴思路，不直接复制代码。
5. **停止猜测**：同一路径连续两次没有进展，换信息源或方法；三次仍无结果，报告已尝试内容、证据和阻塞点，不再生成更多未经验证的变体。

T0/T1 默认走这条低成本路径；T2 可以扩大检索和验证，但仍先检查已有方案。高风险、安全或数据问题需要独立审查时，使用可用的独立 reviewer/subagent；没有独立审查资源就明确标记自查范围。

## 分档

| 档位 | 适用范围 | 做法 |
|---|---|---|
| T0 直改 | 文案、样式、小而明确的缺陷，不改变数据/API/权限契约 | 定位、修改、跑相关检查；不写计划文档 |
| T1 单点 | 一个用户可感知功能，边界清楚，集中在单一垂直切片 | 简短对齐验收与非目标；实现、测试、回报证据 |
| T2 全流程 | 新产品、多层改动、含登录/数据迁移/外部集成，或高风险与多项取舍 | 读取 [全流程](references/workflow.md)，按需用 [全栈检查表](references/fullstack-checklist.md)；先建立可判定目标、契约和分步计划，再逐片实现并验证 |

拿不准先用 T1；实际复杂度上升时升 T2。降档不意味着跳过必要安全与回归检查。

## 贯穿规则

- **保留现场**：遵守仓库栈、锁文件、组件与命名约定。不要为局部功能另起框架、依赖、状态管理或抽象层。
- **设计即验收**：用户界面有明确的信息层级、状态与键盘/窄屏体验；沿用现有视觉语言，只有新建产品或被要求重设计时才建立新视觉方向。
- **契约先行**：跨 UI/API/服务/数据库的改动先核对输入、输出、错误、身份与数据所有权；新功能尽量做一条端到端切片，不造空壳层。
- **数据可逆**：迁移先检查现有 schema、数据量和部署约束；破坏性迁移、数据删除、生产变更需明确范围及回滚/恢复方式。
- **验证说真话**：执行适合本次改动的测试、lint、类型检查或构建；UI 改动在可用环境中实际浏览。报告命令、结果和未能覆盖的部分，不把“写了测试”说成“测试通过”。
- **先查根因**：缺陷先复现、读完整报错并追到出错边界；一次验证一个假设，不把顺手重构混进修复。
- **外部动作有边界**：代码修改本身不代表允许 push、开 PR、部署、发布、改线上数据或产生费用。只有用户明确点名动作及目标后才做；有破坏性或范围不清时先确认。
- **适度审查**：多层、安全、数据迁移或用户要求审查时再做独立审查或专项审计；小改不强制写报告。更多方法、来源及纪律见 [方法与沟通](references/principles.md) 和 [优质技能索引](references/skill-ecosystem.md)。

## 完成交付

确认目标和非目标都已覆盖；必要检查已实际执行；查看最终 diff，确保没有无关/秘密文件；说清改了什么、验证了什么、遗留风险和未执行的外部动作。只有用户要求时才提交、推送或发布。
